클로드 대화창 바뀔 때마다 설명하기 지쳐서, GitHub에 AI의 뇌를 만들었다

2026. 10. 26.
시리즈 · AI 오케스트레이션 만들기
  1. 1부클로드 대화창 바뀔 때마다 설명하기 지쳐서, GitHub에 AI의 뇌를 만들었다

어느 기기, 어느 대화창에서 시켜도 같은 결과가 나오게 하려고 Claude 바깥의 GitHub 저장소에 AI의 뇌를 만들었다.

클로드를 쓰다 보니 어떨 땐 집 PC로, 어떨 땐 노트북으로, 어떨 땐 휴대폰으로 일을 시키고 있었다. 또 어떨 땐 이 대화창에서, 어떨 땐 저 대화창에서 했다. 너무 복잡해졌다. 그렇다고 새 대화창을 열면 이전 글을 불러오고, 어디까지 했는지 설명하는 과정이 또 필요하다. 그게 너무 귀찮아졌다.

먼저 말해 두면, 이 작업은 오케스트레이션을 만들어 가는 과정의 일부고 그 작업기록이다. 솔직히 꽤 비효율적인 방법이라고 생각한다. 더 효율적인 방법을 이미 많은 사람들이 구축해 놨을 거다. 그래도 내가 한 과정을 공유하려고 남긴다.

내가 원한 건 하나였다

웹에 뇌를 두고, 어떤 기기에서 요청을 하든 그 뇌(GitHub)를 거쳐 정해진 과정(스킬, md 문서들)대로 일정한 결과물이 나오는 것. 겉에서 보면 「그렇게 하면 되는 거 아니야?」 싶은데 쉽지 않았다. 거의 일주일을 이 시스템 만드는 데 썼다. 수많은 대화창, 수많은 테스트, 수많은 토큰을 날렸다. 그리고 아직도 최적화하는 중이다.

내 환경은 이렇다. 이게 다 따로 놀아서 문제였다.

구분 내가 쓰는 것
기기 집 PC, 회사 PC, 노트북, 휴대폰
Claude 계정 개인 둘, 회사 하나. 계정 3개
대화창 데스크톱 앱 채팅, Code 탭, 클라우드 세션, 모바일 앱
결과물 강PD 로그, 다국어 사이트 Cutroom Notes(5개 언어), 네이버 블로그

Claude에도 메모리가 있다. 그런데 계정마다 따로 쌓인다. 한 계정 메모리에는 회사 블로그 규칙이, 다른 계정에는 개인 블로그 규칙이 섞여 들어갔다. 새 창이 엉뚱한 규칙을 따라가는 일이 생겼다. 그래서 기억을 Claude 안이 아니라 밖에 두기로 했다.

일주일 동안 해 본 것들

처음부터 지금 구조로 온 게 아니다. 실패한 시도가 더 많다.

날짜 시도 결과
10/23 저장소 문서 하나에 지시를 적어 두면 감시 프로그램이 1~2시간마다 확인해서 분야별 담당 대화창(블로그·네이버·프리미어)에 일을 보내는 구조를 설계 방향만 정함
10/24 할 일 큐를 GitHub Issues로 옮김. 라벨 11종(분류필요·대기중·진행중·막힘, 담당별, PC별), 이슈 양식, 운영 규칙 문서 작성 뼈대는 섰다
10/24 예약 작업 「지휘 세션」을 09시부터 23시까지 2시간마다 돌려 새 이슈를 분류·배정 분류는 잘 됐다. 담당 대화창을 띄우는 건 안 됐다
10/24 GitHub Actions에서 제미나이 API로 번역을 자동으로 돌리는 워크플로 429·503 오류로 불안정하고 토큰도 더 들어서 되돌림
10/24 다 접고 「블로그 글 쓰자」 한 명령으로 정해진 절차를 끝까지 도는 스킬 하나로 정리 지금 방식의 출발점
10/25 계정 3개·PC 여러 대 공통 구조. 원본은 저장소 하나, 계정과 PC에는 입구만 위 시작판이 이때 나왔다
10/25 PC 폴더에 저장하는 것도 없앰. 작업 공간은 GitHub 하나 지금 구조

제미나이 API는 꽤 기대했다. Claude 한도와 상관없이 번역 같은 일을 맡기면 좋을 것 같았다. 그런데 제미나이와 클로드를 둘 다 설득해야 하더라. 둘 중 하나라도 삐끗하면 작업량이 두 배가 됐다. 그래서 일단 클로드로만 가기로 했다.

예약 작업으로 깃을 일정 시간마다 조회하게 해서, 파일이 바뀌면 알아서 작업하게도 해 봤다. 문제는 법전(글 쓰는 규칙 문서)을 고칠 때마다 그것도 변화로 잡혀서 조회가 돌았다는 거다. 토큰만 샜다. 게다가 예약 작업으로 뜬 세션은 다른 대화창을 새로 띄우는 기능이 없었다. 두 번 돌려서 확인했다. 결국 자동 감시는 실패로 접었다. 하더라도 제일 마지막에, 설계가 다 끝났을 때 붙일 생각이다.

지금 구조: 입구는 얇게, 뇌는 저장소에

직접 그린 구조도다. 핵심은 계정과 PC에는 거의 아무것도 두지 않는 것이다.

층 무엇이 있나 어디에
입구 「블로그 연결」이라고 하면 저장소부터 읽으라는 짧은 지시 계정마다 스킬 하나(blog-connect), Claude Code를 쓰는 PC에는 전역 지침 한 블록
뇌 시작 지침, 작업일지, 법전, 글쓰기 절차 스킬 비공개 저장소 blog-notes
결과물 글, 번역, 사진 공개 저장소 두 개(강PD 로그, Cutroom Notes)

입구에는 규칙을 안 적는다. 규칙을 적으면 계정마다 버전이 달라지고, 고칠 때 세 군데를 다 고쳐야 한다. 입구가 하는 일은 「저장소에 가서 이 순서로 읽어라」뿐이다. 입구에 버전 번호(v1)를 붙여 두고, 저장소 쪽 시작 지침과 번호가 다르면 「입구를 갱신해 달라」고 한 줄 말하게 했다.

새 계정을 붙일 때는 이 칸만 따라 하면 된다. 저장소를 못 읽는 창이면 스킬 원문을 통째로 붙여 넣어 등록한다.

뇌 역할을 하는 비공개 저장소다. 새 창은 여기서 이 순서로만 읽는다.

순서 파일 읽는 범위
1 CLAUDE.md 전부. 짧은 시작 지침
2 작업일지.md 「지금 상태」만. 통독 금지
3 계획/준구블로그_법전.md 지금 하는 일에 필요한 장만
4 .claude/skills/blog-write 글쓰기 절차 중 해당 절만

통독을 막아 둔 건 토큰 때문이다. 작업일지 전체를 매번 읽으면 그것만으로 한도가 줄어든다. 끝낼 때는 작업일지의 「지금 상태」를 고치고 커밋·푸시까지 해야 한다. 푸시 안 한 작업은 다른 기기에서 안 보인다.

중간에 실제로 사고도 났다. 다른 창이 회사 블로그용 법전을 가져와서 일했다. 작업 폴더 맨 위에 이름에 「법전」이 들어간 회사 문서가 있어서 검색에 먼저 걸린 거였다. 그래서 시작 지침에 「이 블로그들의 법전은 이 파일 하나다」라고 못 박았다. 사진 크기 같은 규칙을 나한테 되묻기 전에 법전에서 먼저 찾으라는 줄도 넣었다.

이렇게 실제로 겪은 증상은 시작판 「안 될 때」 칸에 하나씩 쌓았다.

시작판 HTML도 남긴다

맨 위 사진이 그 시작판이다. 새 계정, 새 PC를 붙일 때마다 헷갈려서 한 장짜리 HTML로 만들었다. 대화창 열 때, 끝낼 때, 새 계정 처음, 새 PC 처음, 안 될 때, 어디에 뭐가 있는지까지 일곱 칸이다. 원래는 명령마다 「복사」 버튼만 있었다. 공개본은 버튼을 빼고 안의 명령과 문구를 전부 펼쳐 보이게 다시 저장했다.

블로그 연결 시작판 공개본 열기

10월 25일 낮 기준이다. 그 뒤로 「PC 폴더에 저장하지 않고 GitHub 하나만 쓴다」로 한 번 더 바뀌어서, 시작판의 PC 폴더 경로나 파워쉘 푸시 명령은 지금은 거의 안 쓴다. 회사 관련 표기 몇 군데는 일반 표현으로 바꿨다.

결과물이 쌓이는 공개 저장소다. 커밋 기록에 나와 claude가 같이 찍힌다. 어느 창에서 일했든 결과는 여기로 모인다.

이 글도 그 구조로 썼다. 오늘 새 대화창에서 「블로그 글쓰자」라고만 했다. 창이 입구 스킬을 읽고, GitHub에서 저장소를 받아 작업일지를 읽고, 다음 할 일을 한 줄로 보고했다. 어떤 블로그냐고 묻지 않았다. 처음 저장소를 받을 때 인증이 없어 한 번 막혔고, 세션에 저장소를 추가하는 방식으로 다시 받았다. 이런 자잘한 걸리는 지점이 아직 남아 있다.

남은 건 자동 감시다. 지금은 내가 창을 열고 한마디는 해야 한다. 설계가 다 끝나면 그때 마지막에 붙여 볼 생각이다.
