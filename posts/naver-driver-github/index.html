네이버 블로그 입력기, PC 폴더·로컬 서버 없이 GitHub에서 읽게 바꾼 과정

  3. 3부네이버 블로그 입력기, PC 폴더·로컬 서버 없이 GitHub에서 읽게 바꾼 과정

네이버 이관을 맡겼더니 클로드가 PC 폴더와 로컬 서버가 있어야 돌던 입력기를 GitHub에서 원고와 사진을 바로 읽는 방식으로 바꿔 놓았고, 이제 PC에는 로그인된 웨일 창 하나만 있으면 된다.

10월 28일 새벽, 결혼식 식중영상 1~4부를 네이버로 옮겨 달라고 했다. 클로드는 네 편을 임시저장하는 도중에 입력기를 새로 고쳐 썼고, 일이 끝난 뒤 그 사실을 보고 끝에 한 줄로 알렸다.

새 입력기의 커밋 기록. 맨 아래가 첫 판이고, 위로 갈수록 막힌 곳을 하나씩 고친 판이다

입력기는 플레이라이트로 웨일 창을 조작해 네이버 편집기에 글을 넣는 스크립트다. 플레이라이트가 손이라면 입력기는 그 손에 쥐여 주는 작업 순서표다. 원고를 읽어서 제목, 인용구 소제목, 표, 사진을 어떤 순서로 넣을지 정한다. 이번에 바뀐 건 손이 아니라 순서표 쪽이다.

규칙은 GitHub 하나인데 입력기는 PC에 묶여 있었다

10월 25일에 블로그 작업 공간을 GitHub 하나로 정했다. 어느 계정, 어느 PC, 휴대폰에서 열어도 같은 상태에서 이어지게 하려는 것이었다. 그래서 PC 폴더에는 저장도, pull도 하지 않는다는 규칙을 시작 지침에 넣었다.

10월 25일 시작 지침 변경. PC를 판별하던 줄이 빠지고 「작업 공간은 GitHub뿐」이 들어갔다

그런데 네이버 입력기는 그 전 방식 그대로였다. 예전 입력기(naver_driver.js)를 돌리려면 PC에서 이런 준비가 필요했다.

준비 예전 입력기
원고 PC의 blog-notes 폴더에서 python -m http.server 8125로 로컬 서버를 켜서 읽음
사진 플레이라이트가 허용한 PC 폴더에 up0.webp, up1.webp 이름으로 복사
설정 입력기를 같은 폴더에 drv.js로 복사, naver_params.json에 원고 이름과 시작 위치 기록
사진 넣기 사진 자리에서 멈추면 browser_file_upload로 올리고 다시 실행

규칙대로라면 이 중 PC 폴더를 쓰는 일은 전부 할 수 없다. 이틀 전 쿠팡 후기 글 때는 클라우드 창이 이걸 손으로 돌아갔다. 썸네일은 PC 브라우저 안에서 캔버스로 직접 그렸고, 사진은 강PD 로그 공개 주소에서 불러와 하나씩 붙여 넣었다.

주소 두 개로 먼저 시험했다

클로드는 원고 네 편과 썸네일을 먼저 GitHub의 비공개 저장소에 올렸다. 재료가 PC가 아니라 저장소에 있어야 규칙과 맞기 때문이다.

그다음 바로 입력기를 만들지 않고 시험부터 했다. 웨일은 내 GitHub 계정에 로그인돼 있다. 그렇다면 웨일이 비공개 저장소 파일도 받아 올 수 있지 않을까. 썸네일 하나와 원고 하나, 주소 두 개를 웨일에서 요청해 봤고 둘 다 받아졌다.

이 시험 하나로 PC 폴더가 필요 없어졌다. 원고와 썸네일은 비공개 저장소에서, 본문 사진은 이미 발행된 강PD 로그 주소에서 받으면 된다. 원고 머리말에는 사진 폴더 이름(imgdir)만 한 줄 적어 두면 된다.

재료 새 입력기가 가져오는 곳
원고 blog-notes 비공개 저장소 네이버/*.md
썸네일 같은 저장소 네이버/썸네일/<슬러그>.webp
본문 사진 강PD 로그 images/<imgdir>/ 공개 주소
입력기 자체 같은 저장소 tools/naver_driver_gh.js, 커밋 번호로 고정

입력기도 GitHub에서 읽는다. 웨일에 「이 커밋의 입력기를 받아서 실행해」라고 넘기는 식이다. 커밋 번호를 박아 두니 고칠 때마다 새 커밋을 올리고 그 번호로 다시 부르면 된다.

async (page) => {
  const SHA = '<커밋 번호>';
  const s = await (await page.request.get('https://github.com/kelvin-KangPD/blog-notes/raw/' + SHA + '/tools/naver_driver_gh.js')).text();
  return await eval(s)(page, { SHA, FILE: '<원고 파일>', PHASE: 'write', START: 0, CLEAR: true });
}

플레이라이트 코드는 한 번에 60초 안에 끝나야 한다. 그래서 입력기는 40초가 지나면 「여기까지 넣었다」는 번호를 돌려주고 멈춘다. 그 번호부터 다시 부르면 이어서 넣는다. 본문을 다 넣고 나면 마무리 단계를 따로 불러 표 스타일 「표2」, 사진 크기(대표 사진 가로 600, 늘어난 사진은 원본 가로), 본문 글꼴 나눔스퀘어, 임시저장까지 한다.

사진에서 두 번 막혔다

첫 판을 돌리자 막힌 건 사진이었다. 9분 동안 커밋이 여섯 개 쌓였다.

시각 바꾼 것 이유
1:03 첫 판 PC 폴더·로컬 서버 없이 GitHub에서 원고·사진 읽기
1:04 사진을 파일 선택창으로 파일 입력칸에 직접 넣는 방식이 안 먹힘
1:06 사진을 붙여넣기 이벤트로 파일 선택창은 플레이라이트가 가로채서 쓸 수 없음
1:06 이미 글쓰기 화면이면 다시 열지 않기 새로 열 때마다 「나가시겠습니까」 안내창이 뜸
1:09 사진 넣기 전 커서 잡기, 위치 확인 표나 사진 바로 뒤에서는 커서가 안 잡혀 사진이 글 맨 위로 들어감
1:12 본문 완전히 비우기, 사진 기다림 늘림 새 글 칸이 덜 비워진 채 시작되는 걸 막고, 사진이 다 들어오기 전에 다음으로 넘어가지 않게

붙여넣기 방식은 이틀 전 다른 대화창이 찾아서 스킬에 적어 둔 것이었다. 사진 파일을 편집기 안에서 파일 객체로 만들어 「붙여넣기가 일어났다」는 신호와 함께 보내면, 네이버 편집기는 사람이 Ctrl+V 한 것처럼 사진을 받는다. 클로드는 막히자 그 기록을 가져다 입력기에 넣었다.

커서 문제는 입력기 주석에 그대로 남아 있다. 표를 넣은 직후에는 편집기가 커서를 표 밖으로 못 옮겨서, 사진이 엉뚱하게 글 맨 위에 들어갔다. 글자 하나를 쳤다가 지우는 것으로 커서를 잡고, 사진이 들어간 뒤에는 마지막 블록이 사진인지 확인해서 아니면 멈추게 했다.

네 편이 7분 사이에 들어갔다

여섯 번째 판으로 1부부터 4부까지 차례로 넣었다. 1부가 1시 11분, 4부가 1시 18분에 임시저장됐다.

임시저장 목록. 1~4부가 7분 사이에 차례로 들어갔다. 맨 아래 27일 글은 예전 짧은 판이다

PC에서 한 준비는 하나도 없었다. 서버를 켜지도, 사진을 복사하지도 않았다. 웨일 창이 켜져 있고 네이버와 GitHub에 로그인돼 있으면 끝이다.

일을 마친 뒤 클로드는 스킬에 새 입력기 사용법을 한 줄 적었다. 다만 예전 입력기를 쓰는 옛 절차는 그대로 남아 있었다. 몇 시간 뒤 다른 창이 시작 지침과 스킬이 서로 다른 말을 한다는 걸 짚었고, 정리하라고 하자 옛 절차를 걷어 냈다.

정리한 시작 지침. 로컬 서버를 켜라던 줄이 「필요 없다」로 바뀌었다

PC는 웨일 창 하나만 빌려 쓴다

지금 구조에서 PC가 맡는 건 로그인된 브라우저뿐이다. 클라우드 창에서 일하다가 PC 웨일이 필요할 때만 빌려 쓴다.

일 어디서
원고·썸네일 작성, 사진 변환, 강PD 로그·다국어 발행 클라우드 창(GitHub 저장소)
네이버 임시저장 PC 웨일 창(새 입력기가 GitHub에서 읽어서 넣음)
웹 화면 캡처 PC 웨일 창에서 찍어 클라우드로 받아 옴
웨일이 꺼져 있을 때 원고만 만들어 네이버/대기열.md에 쌓아 둠

이 글의 캡처도 같은 식으로 받았다. 웨일에서 GitHub 화면을 찍어 이미지 데이터를 글자로 바꿔 돌려주게 하고, 클라우드 쪽에서 다시 그림 파일로 되돌렸다. 썸네일에 쓰는 글꼴도 클라우드에서는 내려받는 주소가 막혀 있어서, 웨일이 대신 받아 두 번에 나눠 넘겨줬다.

규칙과 도구가 어긋난 자리에서 멈추지도, 규칙을 어기지도 않고 싼 시험으로 길이 있는지부터 본 것. 그다음 한 번에 하나씩 고쳐 가며 네 편을 끝까지 넣은 것. 이번 일은 클로드가 일을 잘했다.
